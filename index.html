Project 30: Production Data Entry App + Dashboard

Tujuan project: membangun aplikasi input data produksi yang tervalidasi untuk menggantikan pencatatan Excel manual, yang langsung menampilkan yield dan NG rate per stasiun, model, dan supplier, sehingga masalah kualitas terlihat di hari yang sama dan waktu rekap manual bisa dihemat.

Kategori:Rancangan projectManufaktur smartphoneData simulasiAplikasi Streamlit + SQL

Project Introduction

Bayangkan warung yang mencatat penjualan di buku tulis. Kasir menulis nama barang dan jumlahnya dengan tangan. Kadang tulisan sulit dibaca, kadang jumlah salah ditulis, kadang ada transaksi yang lupa dicatat. Setiap malam pemilik warung menjumlahkan semuanya dengan kalkulator, dan kesalahan baru ketahuan berhari-hari kemudian.

Lalu warung beralih ke aplikasi kasir. Kasir tinggal memilih barang dari daftar, total dihitung otomatis, dan aplikasi menolak jumlah yang tidak masuk akal. Laporan penjualan langsung tersedia kapan saja, tanpa perlu menghitung ulang.

Project ini meng-upgrade aplikasi Streamlit lama menjadi aplikasi input dan dashboard yang aman, tervalidasi, dan teruji. Kode lama dirapikan, kredensial yang sempat tersimpan di repositori dibersihkan, lalu hasilnya dilengkapi analisis dengan temuan berangka. Datanya adalah data simulasi karena data pabrik bersifat rahasia. Kata bergaris bawah putus-putus kuning bisa diklik untuk melihat artinya.

Gambaran alur kerja di lini perakitan smartphone

Lini produksi bisa dibayangkan sebagai tiga jalur. Jalur pertama adalah proses produksi. Jalur kedua adalah cara mencatat yang dipakai saat ini. Jalur ketiga adalah yang dibangun di project ini untuk menggantikan jalur kedua.

  1. Jalur produksi. Komponen melewati 10 stasiun secara berurutan, dari Solder Paste Printing sampai Packaging. Di setiap stasiun, operator menghitung jumlah OK dan NG untuk setiap tray.
  2. Pencatatan saat ini. Operator mengetik hasil di Excel tanpa pengecekan. File tersebar per stasiun dan per bulan, lalu engineer merekap secara manual. Salah ketik baru ketahuan saat laporan disusun.
  3. Form input tervalidasi. Operator memilih stasiun, model, dan supplier dari daftar, lalu mengisi jumlah OK dan NG. Aplikasi menolak isian yang tidak masuk akal dan menjelaskan apa yang harus diperbaiki.
  4. Database dan dashboard. Data yang lolos validasi langsung tersimpan di database. Dashboard membaca data itu dan menampilkan yield, NG rate, dan tren tanpa rekap manual.

1. BackgroundKenapa tema ini dipilih

Latar belakang masalah

Di lini perakitan smartphone, hasil kerja setiap tray (jumlah OK dan NG, model, batch, supplier, operator) masih dicatat di Excel. Aplikasi Streamlit yang sudah pernah dibuat juga belum siap dipakai karena masalah keamanan dan validasi. Akibatnya:

  • Isian bebas membuat data kotor: nama model ditulis berbeda-beda, kolom kosong, atau jumlah OK dan NG keliru.
  • Engineer menghabiskan waktu setiap minggu untuk menggabungkan dan membersihkan file sebelum bisa menghitung yield.
  • Masalah di satu stasiun atau supplier baru terlihat saat laporan bulanan, saat kerugiannya sudah terjadi.
  • Di repositori aplikasi lama, file berisi kredensial database ikut tersimpan, sehingga siapa pun yang membuka repositori bisa mengakses database.

Alasan memilih tema ini sebagai portofolio

  • Dekat dengan pekerjaan sehari-hari. Pencatatan output dan NG per tray adalah pekerjaan rutin di lini, dan masalah data kotornya dialami langsung.
  • Menunjukkan skill Data Analyst yang lebih lengkap. Selain analisis dan dashboard, project ini menunjukkan cara mencegah data kotor sejak awal, menulis query yang aman, menguji kode, dan mengamankan kredensial.
  • Tingkat kesulitan sulit. Analisisnya deskriptif, tetapi bagian aplikasi, keamanan, unit test, dan deploy menambah beban teknis.
  • Terhubung dengan project lain. Memakai definisi yield dari Project 3, melanjutkan ide anti-bypass dari Project 19 dan ETL dari Project 33, dan datanya bisa dipakai di Project 17 (Supplier Quality Scorecard) dan Project 23 (Telegram Bot KPI Reporting).

4. DatasetData simulasi yang meniru struktur data produksi perakitan smartphone

Kenapa data simulasi? Data pabrik bersifat rahasia. Data dibuat dengan program Python yang mengikuti struktur tabel production_data di aplikasi lama: stasiun, model, batch, tray, supplier, OK/NG, dan operator. Ada dua kelompok data: data "Excel lama" yang sengaja dibuat kotor sebagai pembanding, dan data seed yang dimasukkan lewat aplikasi.

Ukuran: 10 stasiun, 3 model, 4 supplier, 2 shift, sekitar 16 operator, sekitar 75 hari kerja. Perkiraan jumlah baris: ±30.000 baris tray di data Excel lama dan ±30.000 baris di data aplikasi. Jumlah pastinya baru diketahui setelah data dibuat.

Sumber data: data simulasi buatan sendiri, dibuat oleh skrip scripts/generate_data.py di repositori project (Versi: v1, rancangan; Tanggal dibuat: saat Tahap B dikerjakan). Data seed kecil ikut disertakan di repositori. Tidak memakai data perusahaan.

Fakta yang sengaja ditanam (ground truth)

1. Satu supplier modul kamera (usulan: Supplier C) dibuat NG rate-nya sekitar 2 kali lebih tinggi di Functional Test.

2. Model Pro dibuat yield-nya lebih rendah di Component Placement karena jumlah komponennya lebih banyak.

3. Satu batch bermasalah selama ±4 hari menaikkan NG di Reflow Soldering dan AOI Inspection.

4. Operator baru dibuat lebih sering NG di 2 minggu pertama, lalu membaik.

5. Sekitar 2–3% data Excel lama dibuat kotor: salah ketik model, kolom kosong, OK + NG bernilai 0 atau melebihi kapasitas tray, baris ganda, supplier tidak dikenal.

Empat tabel yang akan dibuat

Data disimpan dalam beberapa tabel yang saling terhubung, seperti beberapa sheet Excel yang dihubungkan lewat kolom yang sama. Tabel production_data mengikuti aplikasi lama, tiga tabel lainnya baru ditambahkan untuk validasi dan jejak perubahan.

5. ToolsAlat yang dipakai dan alasannya

Python (Streamlit, pandas)

Streamlit membangun form input dan halaman dashboard dalam satu aplikasi. pandas dipakai untuk membuat data simulasi, membersihkan data Excel lama, dan cek silang.

Aplikasi lama sudah memakai Streamlit, jadi upgrade tidak perlu mulai dari nol.

SQLAlchemy + SQL

Lapisan penghubung ke database. Semua query memakai parameter, dan fitur edit hanya menerima nama kolom dari whitelist. Query KPI disimpan sebagai view.

Kode yang sama bisa berjalan di SQLite dan PostgreSQL. psycopg2 dipakai sebagai driver PostgreSQL.

SQLite + PostgreSQL (Neon)

SQLite untuk pengembangan dan test di komputer sendiri. PostgreSQL di Neon untuk demo online yang bisa diisi beberapa orang sekaligus.

Keduanya gratis. DuckDB tidak dipakai di aplikasi karena kurang cocok untuk banyak penulis data sekaligus.

Plotly

Grafik interaktif di dashboard: yield per stasiun, Pareto NG, NG rate per supplier, dan tren harian.

Menyatu dengan Streamlit dan konsisten dengan project lain di portofolio ini.

pytest + GitHub Actions

Unit test untuk aturan validasi, query, dan perhitungan KPI. GitHub Actions menjalankan test otomatis setiap ada perubahan kode.

Bukti bahwa aplikasi diuji, bukan hanya dicoba manual. Badge status test tampil di README.

git filter-repo + gitleaks

git filter-repo menghapus file .env dan key JSON dari seluruh riwayat commit. gitleaks memindai ulang repositori untuk memastikan tidak ada kredensial tersisa.

Menghapus file di commit terbaru saja tidak cukup karena file lama masih bisa dibuka dari riwayat.

Streamlit Community Cloud

Tempat aplikasi dipublikasikan agar bisa dibuka lewat link. Kredensial database disimpan di st.secrets, bukan di kode.

Gratis dan langsung terhubung ke repositori GitHub.

Docker (opsional)

Membungkus aplikasi beserta semua library-nya agar bisa dijalankan sama persis di komputer mana pun.

Berguna untuk menunjukkan kesiapan deploy di server pabrik. Tidak wajib untuk demo online.

GitHub + Markdown

Menyimpan kode, data seed, dan README berisi screenshot, diagram alur, insight, dan link demo.

Recruiter melihat project langsung dari repositori.

Tahap A · Perencanaan

  1. Mengaudit repositori lama dan error di Excel

    Mendata struktur kode, tabel, dan masalah di aplikasi lama. Mengelompokkan jenis error di data Excel, lalu menurunkan satu aturan validasi untuk tiap jenis error (Q1).

    Hasil: laporan audit dan daftar aturan validasi · Alat: Markdown

  2. Mengamankan repositori

    Menghapus file .env dan key JSON dari repositori dan seluruh riwayat commit, mengganti kredensial lama, menambah .gitignore, dan memindahkan kredensial ke st.secrets. Hasilnya dipindai ulang dengan gitleaks (Q12).

    Hasil: repositori bersih dan catatan keamanan · Alat: git filter-repo, gitleaks

Tahap B · Menyiapkan data & aplikasi

  1. Merancang skema dan membuat data simulasi

    Menetapkan 4 tabel dan kamus data. Program Python membuat data Excel lama yang kotor dan data seed yang bersih, termasuk fakta yang ditanam.

    Hasil: skema SQL, CSV, catatan ground truth · Alat: Python, SQL

  2. Membangun form input tervalidasi

    Form dengan dropdown dari tabel ref_master, pengecekan jumlah dan format, serta pesan error yang jelas. Isian yang ditolak dicatat di rejected_input (Q1–Q3).

    Hasil: halaman input aplikasi · Alat: Streamlit

  3. Membangun lapisan database yang aman

    Semua akses database lewat satu modul dengan parameterized query. Fitur edit hanya menerima kolom dari whitelist dan mencatat perubahan di edit_log (Q13).

    Hasil: modul database · Alat: SQLAlchemy, SQLite, PostgreSQL

Tahap C · Menghitung dan menganalisis

  1. Menulis unit test dan CI

    Test untuk setiap aturan validasi, percobaan SQL injection, whitelist kolom, dan rumus KPI. GitHub Actions menjalankan test di SQLite dan PostgreSQL (Q13, Q15).

    Hasil: folder tests dan workflow CI · Alat: pytest, GitHub Actions

  2. Menulis query KPI dan cek silang

    Membuat view SQL untuk yield, NG rate, kelengkapan input, dan error rate. Beberapa sampel dihitung ulang dengan pandas dan Excel untuk memastikan hasilnya sama (Q14).

    Hasil: view KPI dan lembar cek silang · Alat: SQL, pandas, Excel

  3. Menganalisis yield, NG, dan supplier

    Menjawab Q4–Q9: peringkat stasiun, perbedaan model, NG rate per supplier dan batch, tren harian, dan kelompok operator. Hasilnya dirangkum menjadi minimal 3 insight berangka.

    Hasil: grafik dan daftar insight · Alat: SQL, Plotly

  4. Menghitung dampak

    Menghitung error per 1.000 entri sebelum dan sesudah aplikasi, jam rekap dihemat per tahun, dan unit terselamatkan jika NG teratas turun 10%, 20%, dan 30% (Q2, Q10, Q11). Semua angka diberi label estimasi.

    Hasil: tabel skenario dampak · Alat: pandas

  5. Mencocokkan dengan fakta yang ditanam

    Memeriksa apakah dashboard dan analisis menemukan semua kejadian yang ditanam di langkah 3. Jika ya, metode terbukti bekerja.

    Hasil: bagian validasi di README · Alat: Python

Tahap D · Menyajikan

  1. Membuat dashboard dan deploy

    Dashboard 4 halaman: Ringkasan, Stasiun & Model, Supplier & Batch, dan Kualitas Input. Aplikasi dipublikasikan di Streamlit Community Cloud dengan database Neon.

    Hasil: link demo aplikasi · Alat: Streamlit, Plotly, Neon

  2. Menulis README dan finalisasi

    README berisi masalah, insight utama, rekomendasi, dampak, batasan, screenshot, diagram alur, dan link demo. Insight ditaruh di atas, sebelum daftar fitur aplikasi.

    Hasil: repositori GitHub siap ditinjau · Alat: Markdown, GitHub

9. Assumptions & LimitationsKomponen tambahanKeputusan yang sudah diambil dan hal yang perlu diwaspadai

Jenis data: simulasi meniru data kerja Sudah Anda setujui

Data dibuat dengan program dan mengikuti struktur production_data dari aplikasi lama. Angka hasil akhir membuktikan bahwa aplikasi dan metodenya bekerja, bukan menggambarkan kondisi pabrik sebenarnya.

Database: SQLite lokal + PostgreSQL untuk deploy Sudah Anda setujui

SQLite untuk pengembangan dan test, PostgreSQL di Neon (free tier) untuk demo online. Kolom Tools di daftar portofolio menyebut "PostgreSQL (Neon/Supabase) atau SQLite/DuckDB"; Supabase dan DuckDB tidak dipakai, sehingga kolom itu sebaiknya diperbarui.

Kondisi repositori lama Usulan awal

Repositori Streamlit_project_dashboard belum bisa dibaca dari sesi ini. Rancangan ini mengikuti deskripsi di daftar portofolio: ada file .env dan key JSON di repositori, dan tabel production_data berisi station, model, batch, tray, supplier, OK/NG, dan operator. Jika kondisi aslinya berbeda, langkah 1 dan 2 disesuaikan.

Ruang lingkup Usulan awal

10 stasiun perakitan smartphone, model Basic, Plus, dan Pro, 4 supplier anonim, 2 shift, ±3 bulan. Satu baris berarti satu tray di satu stasiun. Login cukup satu kata sandi lewat st.secrets, tanpa pembagian hak akses per peran. Dashboard memakai Streamlit + Plotly. Dampak dihitung dalam jam kerja dan unit, belum dalam rupiah.

Hal yang perlu diwaspadai Usulan awal

Kredensial yang pernah ter-push dianggap bocor. Menghapus file dari riwayat tidak cukup karena salinannya mungkin sudah tersebar. Kredensial lama wajib diganti.

Validasi tidak menangkap semua error. Angka yang keliru tetapi masih masuk akal (misalnya NG 3 tertulis 2) tetap lolos. Bagian ini dijelaskan apa adanya di README.

Data operator. Operator memakai kode anonim. Analisis per kelompok operator dipakai untuk menentukan kebutuhan pelatihan, bukan untuk menilai individu.

Pola belum tentu penyebab. Jika Supplier C lebih banyak NG, itu baru pola. Penyebabnya perlu dicek di lapangan. Pengujian statistik dikerjakan di Project 29 (Root Cause Analysis).

Batas free tier. Database Neon gratis bisa "tidur" saat tidak dipakai dan punya batas kapasitas, sehingga demo pertama bisa terasa lambat.
